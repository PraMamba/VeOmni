**本文是 `docs/analysis/ulysses_sequence_parallelism_analysis.md` 的科普改写版。全文用物流隐喻替代代码和技术术语。零代码，全物流世界观。**

## A. TL;DR 故事

VeOmni 框架面对的核心挑战是：一份发货清单（Prompt）太长了，任何单个站点（GPU）的仓位（显存）都装不下整份清单的加工中间件。Ulysses 序列分段协运方案的思路是：把超长清单切成等份，分给多个站点各加工一段；但在"验货"环节（Attention），每个站点必须看到完整清单才能做对比核验——于是系统通过干线互发（all-to-all），让站点们在"验货前"互换各自那段清单、换回各自那些验货窗口（Attention Heads），验完货后再互换回来。这套"分段-互换-验货-换回"的协运方案，配合拆箱共享制（FSDP）同时运行，能把仓位占用降到原来的 1/P（P 为参与协运的站点数），并且提供同步和异步两种调度模式。

## C. 三层解释

### C.1 一句话版

把一份超长的发货清单切成几段，分给多个站点各管一段；需要核对时，站点们通过干线互相交换信息，核对完再换回来，这样每个站点只需要原来几分之一的仓位。

### C.2 一段话版

当包裹清单（序列）特别长时，单个站点（GPU）的仓位（显存）不够用。Ulysses 序列分段协运的做法是：先把清单均匀切成 P 段，每个站点负责一段。在验货环节（Attention）之前，各站点通过干线互发（all-to-all 通信）把自己手里的清单段拼成完整清单、同时把验货窗口（注意力头）分散到各站——这样每个站看到的是完整清单但只负责一部分验货窗口。验货完成后，再通过一次干线互发把窗口拼回来、清单重新切回片段。这套方案可以将每个站的仓位占用降到 1/P，并且支持同步（先发再算）和异步（边发边算）两种调度模式。

### C.3 技术版

VeOmni 框架的 Ulysses 协运方案基于干线互发（all-to-all）通信原语，在序列维度和验货窗口维度之间做动态切换。整体架构如下：

训练开始前，总控调度中心（ParallelState）根据配置在物流版图（DeviceMesh）上划定协运分组——每 P 个站点组成一个协运组，组内站点共同处理同一份清单。在每个楼层（Transformer Layer）中，流程分四步：（1）每个站点对本地清单段做三联分拣（QKV Projection），生成查询单、索引单、价值单；（2）执行"拼段散窗"干线互发，把清单段维度聚合、验货窗口维度分散，使每个站点持有完整清单但仅负责 H/P 个窗口；（3）各站点独立完成验货（Attention 计算）；（4）执行"拼窗散段"干线互发，恢复原始布局。

异步模式通过"边发边算"策略实现通信-计算重叠：在发出第一份互发请求后，不等回件就开始算第二份分拣单，以此类推。这可以将通信延迟几乎完全隐藏在计算中，理论加速接近 2 倍。整套方案与拆箱共享制（FSDP）协同工作：工具（参数）在拆箱共享组内分存，中间件（激活）在协运组内分段，两者通过复合承运合同分组（dp_shard_sp）统一管理退货差异单（梯度）的对账。

## D. 逐章改写

### D.1 概述——协运方案全貌

**结论先行**：Ulysses 序列分段协运是一套让多个站点合力处理超长清单的方案，通过干线互发在"验货前拼段散窗、验货后拼窗散段"来实现。

**物流解释**：

想象一个物流网络需要处理一份极其长的发货清单——长到任何一个站点的仓位都放不下加工它所需的全部中间件。传统做法是让每个站点各自持有完整清单（多站同款备货/数据并行），但这样仓位浪费巨大。

Ulysses 协运方案的核心思想是"分段合作"：把清单切成 P 段，每个站点只存一段。但验货环节有个刚性需求——每个验货窗口必须看到完整清单才能正确工作。怎么办？答案是干线互发：在验货前，让所有站点把各自的清单段互相交换，同时把验货窗口分散开来。这样每个站点就持有完整清单、但只负责一部分验货窗口。验完后再换回来。

这套方案有两种调度模式。同步模式是"先发完再算"——先完成所有干线互发，再开始计算；简单可靠但通信时站点闲着。异步模式是"边发边算"——发出查询单的互发请求后，不等回件就开始算索引单；利用通信等待时间做有用计算，效率更高。

该方案同时支持不同品牌的站点设备——既能在标准站点（NVIDIA GPU）上运行，也能在国产站点（Ascend NPU）上运行。并且它不关心验货的具体方式——无论用高速验货机（FlashAttention）还是标准验货台（SDPA），协运方案都能配合。

如果没有这套方案，处理超长清单时要么爆仓（OOM），要么只能缩短清单长度，限制了模型处理长文本、高分辨率图片和长视频的能力。代价是每次干线互发都有通信开销，清单越短、站点越多，开销占比越大。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 发货清单 | Prompt / Input Sequence |
| 站点 | GPU |
| 仓位 | VRAM / 显存 |
| 验货窗口 | Attention Head |
| 干线互发 | All-to-All 通信 |
| 序列分段协运 | Ulysses Sequence Parallelism |
| 拼段散窗 | gather_seq_scatter_heads |
| 拼窗散段 | gather_heads_scatter_seq |
| 高速验货机 | FlashAttention |

**三条要点**：
- 协运方案把超长清单切段分给多个站点，通过干线互发在验货前后交换维度，仓位占用降到 1/P
- 同步模式"先发再算"简单可靠；异步模式"边发边算"通信计算重叠，效率更高
- 方案与验货方式无关，支持多种站点设备，但通信开销在短清单场景下占比较大

### D.2 核心算法原理——拼段散窗与拼窗散段

**结论先行**：协运方案通过两次干线互发实现序列维度和验货窗口维度的动态切换，本质是"用通信换仓位"。

**物流解释**：

把协运流程拆开来看，核心就是两次"倒货"。

第一次倒货（拼段散窗）发生在验货前。此时每个站点持有清单的一段（比如站点 0 有第 1-1000 号包裹，站点 1 有第 1001-2000 号包裹），以及全部的验货窗口工具。干线互发之后，每个站点变成持有完整清单的全部包裹、但只有一部分验货窗口工具。这就像四个仓库各有 1/4 的货物和全套检验设备，互相倒货后变成每个仓库有全部货物但只有 1/4 的检验设备。

第二次倒货（拼窗散段）发生在验货后。验完货的结果需要换回原始布局——每个站点拿回自己那段清单的验货结果和全部验货窗口。这是第一次倒货的逆操作。

每次干线互发的通信量与清单长度和站点数有关。对于清单长度 S、中间件宽度 H、P 个站点，每次互发约传输 4SH(P-1)/P 字节。站点越多，每个站点发送的比例越小（P=4 时约 75% 效率，P=8 时约 87.5% 效率），但绝对通信量也在增长。

如果清单长度不能被站点数整除，就需要在切段前先用填充料（padding）补齐长度，干线互发后再拆除填充料。这类似于物流中为了凑整车装载而加入的填充泡沫——不增加有效货物，但保证了均匀分配。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 倒货 | all-to-all 通信 |
| 清单段 | 序列分片 (sequence shard) |
| 验货窗口工具 | Attention Head 参数 |
| 填充料 | Padding |
| 拆填充 | Unpadding |

**三条要点**：
- 两次干线互发实现"清单段 ↔ 验货窗口"的维度切换，验货前拼段散窗、验货后拼窗散段
- 通信效率随站点数增加而提高（P=8 时 87.5%），但绝对通信量也更大
- 不整除的清单长度通过填充料补齐，互发后及时拆除以避免无效计算

### D.3 同步模式——先发完再算

**结论先行**：同步模式下，先完成干线互发再开始验货计算，操作顺序简单清晰，但通信期间站点空闲造成浪费。

**物流解释**：

同步模式的工作流程像传统的物流干线：所有货物装车发出、等回件全部到达后才开始下一步操作。

具体流程如下。每个站点先对本地清单段做三联分拣——生成查询单（Q）、索引单（K）和价值单（V）。注意一个关键细节：此时三联分拣单还是未拆分的整体形态（三维格式），每份包含站点负责的那段清单对应的全部验货窗口信息。

然后执行拼段散窗干线互发。这次互发直接在整体形态的分拣单上操作——把清单段维度聚合、把验货窗口维度分散。互发完成后，每个站点才把整体形态的分拣单拆分成独立的验货窗口格式（四维格式）。这个"先互发、后拆分"的顺序是同步模式的关键特征。

拆分完毕后进行可选的校准称重（QK Normalization），然后执行验货计算。验完后把结果重新打包为整体形态，再做一次干线互发（拼窗散段）恢复原始布局。最后做输出投影得到该层的最终结果。

同步模式还提供一个优化路径：如果三份分拣单（Q、K、V）是合并生成的（融合投影），可以只做一次干线互发而非三次。这就像把三批货物拼成一车发出，减少了发车次数。

如果没有同步模式这种简单可靠的基线，异步模式的正确性就无法验证——测试中总是先用同步模式计算参考结果，再检查异步模式是否与之一致。代价是通信期间所有计算资源闲置，清单越长、浪费越大。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 三联分拣单 | QKV Projection 输出 |
| 查询单 | Q (Query) |
| 索引单 | K (Key) |
| 价值单 | V (Value) |
| 整体形态 | 3D tensor [B, N, hidden_dim] |
| 拆分为窗口格式 | reshape 为 4D [B, N, h, d] |
| 校准称重 | QK Normalization |
| 融合投影 | Fused QKV Linear |

**三条要点**：
- 同步模式在 3D 整体形态上做干线互发，**先互发、后拆分**为 4D 窗口格式——这与异步模式的顺序相反
- 融合投影优化可以将三次干线互发合并为一次，减少通信开销
- 作为可靠基线，同步模式用于验证异步模式的正确性

### D.4 异步模式——边发边算的流水作业

**结论先行**：异步模式通过"发出查询单互发请求后不等回件就开始算索引单"的策略，将通信时间隐藏在计算中，理论加速接近 2 倍。

**物流解释**：

同步模式的瓶颈很明显：干线发货需要时间，发货期间站点空闲。异步模式的解决思路是"发货和分拣交替进行"——发出一批货后不干等，利用等待时间做下一批分拣。

具体来说，异步模式将三联分拣和干线互发融合为一个连续流程。流程开始时，站点先做查询单的分拣，**立即拆分为窗口格式**（注意这与同步模式不同——异步模式先拆分再互发），然后发起查询单的异步干线互发。发出后不等回件，立刻开始索引单的分拣。索引单分拣完毕后同样发起异步互发，然后开始价值单的分拣。价值单互发发出后，此时查询单的回件通常已经到达。站点收到查询单和索引单的回件后，在等待价值单回件的同时做校准称重（QK Normalization）——这又是一次"用等待时间做有用工作"。最后价值单回件到达，三联齐备，开始验货。

反向传播（退货差异单回传）同样采用异步策略，但顺序相反：先发价值单的退货差异、在等待期间做校准称重的反向计算，然后发索引单差异、在等待期间算价值投影的修正量，以此类推。

对于共用验货窗口的模型（GQA），索引单和价值单的窗口数少于查询单。当协运站点数超过索引/价值窗口数时，需要先将少量窗口复制扩展——就像一个仓库只有 2 个检验台但需要分给 8 个站点，就先把 2 个台的工作复制 4 份变成 8 个，分配给各站点；退货时再将复制的差异合并回原始 2 个台。

异步模式还利用校准称重步骤做通信-计算重叠。校准称重支持两种方式：RMS 称重（均方根校准）和标准称重（LayerNorm）。RMS 称重在标准站点和国产站点上均可使用；标准称重目前仅支持标准站点。因此，国产站点上若需要异步模式，必须使用 RMS 称重。

如果不采用异步模式，长清单训练中约一半时间浪费在等待干线互发上。代价是实现复杂度显著增加，前向和反向传播都需要精心安排发货和等待的时序。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 边发边算 | 通信-计算重叠 (comm-compute overlap) |
| 异步干线互发 | async all-to-all |
| 退货差异单回传 | Backward pass / gradient computation |
| 共用验货窗口 | GQA (Grouped Query Attention) |
| 窗口复制扩展 | repeat_interleave for KV heads |
| RMS 称重 | RMSNorm |
| 标准称重 | LayerNorm |
| 标准站点 | NVIDIA GPU |
| 国产站点 | Ascend NPU |

**三条要点**：
- 异步模式**先拆分为窗口格式再互发**，与同步模式"先互发后拆分"的顺序相反
- 通信等待时间被用来做下一份分拣或校准称重，理论上可以完全隐藏通信延迟
- 共用验货窗口场景需要先复制少量窗口再分配，退货时合并复制窗口的差异

### D.5 承运合同分组——谁和谁协运

**结论先行**：总控调度中心根据配置把站点划分为多层嵌套的承运合同分组，确保协运组内的站点知道该跟谁互发、跟谁对账。

**物流解释**：

一个物流网络有 16 个站点，需要用 4 个一组做序列分段协运。总控调度中心的任务就是把这 16 个站点切成 4 个协运组，每组 4 个站点。同一组内的站点互相干线互发，不同组之间互不干扰。

分组过程如下：首先确定协运组大小（比如 4），然后用总站点数除以组大小得到组数（16/4=4 组）。站点 0-3 组成协运组 0，站点 4-7 组成协运组 1，以此类推。每个协运组内部还会建立一个备用通信通道（CPU 组），用于某些需要在办公桌（CPU）端完成的协调工作。

系统还支持"统一协运组"，它是把 Ulysses 协运组和上下文并行组合并后的更大分组。当上下文并行度为 1 时（目前常见情况），统一协运组等同于 Ulysses 协运组。

一个巧妙的设计是"多密钥分组"——同一个物流网络可以为不同类型的货物建立不同的协运组。比如文本货物用 4 个一组，图像货物用 8 个一组。通过密钥管理器切换当前使用的分组，不同模态的加工可以使用不同的协运配置。

总控调度中心还提供状态查询接口，让系统在运行时可以检查"协运组是否已经建立"——这在条件执行协运逻辑时很有用。

如果分组配置错误（比如总站点数不能被协运组大小整除），系统会立即报错。如果没有这套分组机制，站点之间的干线互发就会混乱——不知道该往哪发、从哪收。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 承运合同分组 | ProcessGroup |
| 总控调度中心 | ParallelState + init_sequence_parallel |
| 协运组 | Ulysses SP Group |
| 统一协运组 | Unified SP Group |
| 密钥管理器 | UlyssesGroupKeyManager |
| 备用通信通道 | CPU (gloo backend) Group |
| 状态查询接口 | is_ulysses_sequence_parallel_initialized |

**三条要点**：
- 总控调度中心将站点切分为不重叠的协运组，组内干线互发、组间独立
- 多密钥分组允许同一网络为不同类型货物配置不同的协运策略
- 分组配置必须满足整除约束，否则系统无法启动

### D.6 入库分拣与出库合并——数据预处理与后处理

**结论先行**：货物进入协运流程前需要切段、补齐和对位；离开协运流程后需要合并各段恢复完整清单。

**物流解释**：

在货物正式进入各站点的协运流程之前，需要一系列入库分拣操作。

首先是清单切段。把完整的包裹清单（输入序列）沿长度方向均匀切成 P 段，每段分给一个站点。如果清单长度不能被 P 整除，先用空白包裹（padding value 0）补齐。

然后是退货标签的处理。退货标签（labels）需要特殊处理——在切段之前先整体左移一位（因为验货时每个包裹要与下一个包裹对比），移出的空位用"忽略标签"填充，确保这些填充位不会影响后续的差异计算。

位置编码也需要切段。每个站点只需要自己那段清单对应的位置信息（cos/sin 旋转编码），入库时自动截取。

对于图文混装的多模态货物（VLM），有一种特殊的入库方式：先按缩放倍数补齐（确保补齐后的长度同时满足协运分段和图像合并的双重整除要求），然后切片。这是因为某些视觉处理会将 4 个图像包裹合并为 1 个，如果补齐时没有考虑这个合并因子，合并后可能无法均匀分段。

出库合并是入库的逆操作——各站点的结果通过合并清单（all-gather）操作拼回完整序列，然后拆除填充料恢复原始长度。

框架提供两种拆填充策略：一种是在完整清单上统一拆除末尾填充（全员拆填充），另一种是只在最后一个站点上拆除（末站拆填充）——后者适用于需要在分段状态下就移除填充的场景。

如果入库分拣做得不对（比如退货标签没有左移），整个差异计算就会错位，模型根本无法正确学习。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 入库分拣 | sequence_parallel_preprocess |
| 清单切段 | slice_input_tensor |
| 退货标签 | Labels |
| 忽略标签 | IGNORE_INDEX |
| 退货标签左移 | Label shifting (causal LM) |
| 合并清单 | All-gather (gather_outputs) |
| 图文混装 | VLM 多模态输入 |
| 缩放倍数补齐 | sp_pad_and_slice 的 pad_scale 参数 |
| 全员拆填充 | unpadding_tensor_for_sequence_parallel |
| 末站拆填充 | remove_last_rank_padding |

**三条要点**：
- 退货标签在切段前必须先左移一位并用忽略标签填充，否则差异计算全部错位
- 图文混装货物的入库需要考虑缩放倍数，确保补齐长度同时满足分段和合并的双重整除
- 出库合并后的两种拆填充策略适用于不同场景：全员拆填充用于合并后，末站拆填充用于分段状态下

### D.7 差异对账——损失函数处理

**结论先行**：因为每个站点只看到一段清单的差异，需要通过全网对账（all-reduce）将各段差异汇总为全局平均差异，并在退货回传（反向传播）时正确缩放修正量。

**物流解释**：

在序列分段协运中，每个站点只处理清单的一段，因此每个站点计算出的差异值（loss）只反映自己那段的情况。但训练需要的是全局平均差异——所有段的差异加权平均。

差异对账的流程是这样的：首先，每个站点统计自己那段中有多少个有效包裹（排除忽略标签的填充包裹）。如果某个站点的有效包裹数为零（整段都是填充），系统会自动清除可能出现的异常值（NaN），防止后续计算崩溃。然后，站点将自己的平均差异乘以有效包裹数，转换为差异总和。接着，通过全网对账把所有站点的差异总和和有效包裹总数分别汇总。最后，用全局差异总和除以全局有效包裹总数，得到全局平均差异。

退货差异单回传（反向传播）时有一个关键的修正量缩放规则：每个站点收到的修正量需要乘以"协运站点数 * 本站有效包裹数 / 全局有效包裹数"。为什么需要这个缩放？因为拆箱共享制（FSDP）默认会把修正量除以它管辖的站点数，但协运维度上的站点并没有各自独立的完整数据——它们共同处理同一份清单。如果不补偿这个除法，修正量就会被过度稀释。

在实际训练中，差异对账是通过一个更高层的调度函数完成的。这个函数处理多种类型的差异（文本差异、图像差异等），在协运组内对账有效包裹数，在全局范围对账总包裹数，然后按比例缩放每种差异。它还额外除以协运站点数来补偿拆箱共享制的影响。

底层对账模块和高层调度函数的分工是：底层模块是一个自动记录退货路径的对账单元，处理单个差异值的协运聚合；高层函数是总调度台，管理多种差异类型的全局聚合，并自行处理协运内的包裹数对账。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 差异值 | Loss |
| 差异对账 | reduce_sequence_parallel_loss |
| 全网对账 | All-reduce |
| 有效包裹数 | num_valid_tokens |
| 修正量缩放 | Backward gradient scaling |
| 底层对账模块 | ReduceLoss (autograd Function) |
| 高层调度函数 | mean_global_loss |
| 异常值清除 | torch.nan_to_num |

**三条要点**：
- 差异对账的核心是"先转总和、再全网汇总、最后求全局平均"，确保各段的有效包裹数被正确加权
- 退货回传时的修正量必须乘以"协运站点数 * 本站包裹 / 全局包裹"来补偿拆箱共享制的除法
- 零有效包裹的站点会自动清除异常值，防止对账崩溃

### D.8 拆箱共享制集成——协运与分存的协同

**结论先行**：协运方案与拆箱共享制（FSDP）通过物流版图（DeviceMesh）统一管理，工具在分存组内共享，中间件在协运组内分段，两者通过复合分组协同工作。

**物流解释**：

一个完整的物流网络可能需要同时运行多种分工模式。VeOmni 使用物流版图（DeviceMesh）把所有站点组织成一个多维网格，每个维度代表一种分工。

完整的维度定义有六个：流水线维度（PP）、复制备货维度（dp_replicate）、分存维度（dp_shard）、协运维度（ulysses）、上下文维度（cp）和工具拆分维度（tp）。但维度是按需加入的——只有规模大于 1 的维度才会出现在版图中（分存维度例外，它始终存在）。比如一个只用协运和分存的配置，版图就只有两个维度。

在这个版图上，系统定义了四种复合分组：
- 数据分组：用于数据加载，决定哪些站点处理不同的数据批次
- 分存协运组：用于工具（参数）的拆箱共享，涵盖分存、协运和上下文三个维度
- 协运组：纯粹用于序列并行的干线互发
- 全量对账组：涵盖所有数据和协运维度，用于差异对账

协同工作的逻辑是这样的：工具在拆箱共享制（FSDP）下按"分存协运组"进行分存——每个站点只保管一份工具的碎片，使用时临时合并。中间件（加工中间结果）在协运组内按序列分段。退货差异单在"分存协运组"内全网对账，确保参数更新一致。

这意味着工具在协运维度上是**完全复制**的——协运组内的站点使用相同的工具，只是各自处理不同的清单段和验货窗口。而工具在分存维度上是**碎片化存储**的——使用时需要先从各分存站点收集碎片拼成完整工具。

训练流程在此框架下的完整步骤是：数据入库分拣（切段）→ 每层楼层中的"拼段散窗→验货→拼窗散段"循环 → 输出层生成部分结果 → 差异对账 → 退货差异单回传 → 拆箱共享制在分存协运组内汇总修正量。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 物流版图 | DeviceMesh |
| 分存维度 | dp_shard |
| 复制备货维度 | dp_replicate |
| 协运维度 | ulysses dimension |
| 分存协运组 | dp_shard_sp composite group |
| 全量对账组 | dp_sp composite group |
| 工具碎片 | FSDP sharded parameters |
| 完全复制 | Parameters replicated across SP |

**三条要点**：
- 物流版图的六个维度按需加入，只有实际使用的维度才出现在网格中
- 工具在协运维度上完全复制、在分存维度上碎片化存储——两套分工互不冲突
- 退货差异单在分存协运组内全网对账，确保工具更新在所有相关站点间保持一致

### D.9 调度优化——让货物流转更快

**结论先行**：通过填充料管理、通信-计算重叠和共用验货窗口适配三种手段优化协运效率。

**物流解释**：

**填充料管理**是第一个优化重点。当清单长度不能被站点数整除时，需要补充填充料。框架提供两种拆填充方式：一种是在合并全部清单后统一拆除末尾填充料（适用于需要完整清单的场景）；另一种是只在最后一个站点上拆除（适用于分段状态下就需要去除多余填充的场景）。动态拼单（Dynamic Batching）机制会尽量把清单凑成能被站点数整除的长度，减少填充浪费。

**通信-计算重叠**是异步模式的核心优势。理论上，如果通信时间恰好等于计算时间，异步模式可以实现 2 倍加速——因为通信完全被计算隐藏了。实际加速取决于通信与计算的比值：清单越长、站点算力越弱，计算占比越大，重叠收益越明显；清单短、网络快，通信来不及被隐藏，收益有限。校准称重步骤也被巧妙地安排在等待回件的间隙中，进一步填充空闲时间。

**共用验货窗口适配**针对查询窗口数远多于索引/价值窗口数的模型（如 Llama 3 的 64 个查询窗口 vs 8 个索引/价值窗口）。选择协运站点数时需要满足两个约束：查询窗口数必须能被站点数整除；如果站点数超过索引/价值窗口数，站点数必须是窗口数的整数倍。推荐选择 2、4、8（整除）或 16、32（倍数），避免互质的配置。

协运方案与高速验货机（FlashAttention）完全兼容——干线互发后每个站点持有完整清单和部分窗口，直接传入高速验货机即可。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 动态拼单 | Dynamic Batching |
| 通信-计算重叠 | Comm-Compute Overlap |
| 共用验货窗口适配 | GQA Support |
| 查询窗口 | Q heads |
| 索引/价值窗口 | KV heads |

**三条要点**：
- 动态拼单尽量把清单凑成整除长度，减少填充料浪费
- 异步模式的实际加速取决于通信/计算比，长清单+弱算力场景收益最大
- 共用验货窗口模型的协运站点数必须满足双重整除约束

### D.10 质检验收——测试与验证

**结论先行**：通过"协运模式与非协运模式对比"的方式验证正确性——同一份货物、同样的工具，两种模式的处理结果和退货差异必须一致。

**物流解释**：

验证协运方案正确性的方法很直观：给两套站点配备完全相同的工具，一套用协运模式（多站分段处理），另一套用传统模式（单站处理完整清单）。然后送入相同的货物，比较两者的输出和退货差异单是否一致。

具体来说：先在协运组内切段并分配，协运模式处理完毕后通过合并清单恢复完整输出。将这个输出与传统模式的输出逐个包裹比对。然后计算两种模式下的差异值，触发退货回传，比较各站点工具上积累的修正量是否一致。

异步模式的验证更进一步：不是与传统模式比，而是与同步模式比。因为同步模式已经被验证与传统模式一致，所以异步模式只需要与同步模式一致即可传递保证正确性。

还有边界场景的测试：清单长度不整除时（需要填充料的情况），验证填充不影响最终结果。

如果验证发现不一致，通常是某个环节的修正量缩放配置有误，或者填充料没有正确使用忽略标签。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 质检验收 | Unit Testing |
| 协运模式 | SP mode |
| 传统模式 | DP mode (single-GPU reference) |
| 逐包裹比对 | torch.testing.assert_close |
| 修正量比对 | Gradient consistency check |

**三条要点**：
- 正确性验证的金标准是"协运输出 vs 传统输出"的逐包裹数值一致
- 异步模式通过与已验证的同步模式比对来传递正确性
- 填充料场景的测试确保补齐操作不引入数值误差

### D.11 限制与约束——什么运不了

**结论先行**：协运方案对验货窗口数有整除约束，对部分设备的校准称重方式有限制，且在短清单和小批量场景下通信开销可能得不偿失。

**物流解释**：

协运方案有几个硬性约束。首先是验货窗口数约束：查询窗口数必须能被协运站点数整除——因为干线互发是均匀分配的，不能整除就无法均匀切分。对于共用验货窗口的情况，约束更精确：如果站点数超过索引/价值窗口数，站点数必须是窗口数的整数倍；否则窗口数自然需要能被站点数整除。

国产站点上的异步模式目前支持 RMS 称重的前向和反向计算，但不支持标准称重——因为标准称重使用了仅在标准站点上可用的高速称重器。测试中直接跳过国产站点是因为测试使用了标准称重。如果实际模型使用 RMS 称重，国产站点可以运行异步模式。

有几类货物目前运不了：窗口式验货（Sliding Window Attention）需要站点间有重叠的清单段，与当前的均匀切段方案不兼容；稀疏验货的通信模式与均匀干线互发不匹配；跨库验货（Cross-Attention）需要两份不同的清单，额外的协调复杂度尚未实现。

性能瓶颈方面：清单长度短于 4096 时通信开销可能超过节省的仓位收益；使用高速专线（InfiniBand EDR 及以上）时通信占比很低，加速比受限；小批量（单份清单）时通信延迟难以被计算隐藏。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 验货窗口数约束 | Head count divisibility constraint |
| 高速称重器 | fused_layer_norm_cuda |
| 窗口式验货 | Sliding Window Attention |
| 稀疏验货 | Sparse Attention |
| 跨库验货 | Cross-Attention |
| 高速专线 | InfiniBand |

**三条要点**：
- 查询窗口数必须能被站点数整除；共用窗口场景有额外的倍数约束
- 国产站点异步模式支持 RMS 称重但不支持标准称重
- 短清单、高带宽、小批量三种场景下协运方案可能得不偿失

---

### D.12 最佳实践——协运方案的适用指南

**结论先行**：协运方案最适合长清单、大仓位压力、高算力站点的场景，站点数选择需要平衡窗口数约束、清单长度和可用站点数。

**物流解释**：

推荐使用协运方案的场景：清单长度超过 8192 个包裹，单站仓位不足以容纳完整加工中间件，训练长文本模型、高分辨率视觉语言模型或长视频生成模型。

不推荐的场景：清单长度短于 2048 个包裹（通信开销太大），已经使用了其他分段方案（如 Megatron 式序列并行），或者网络带宽极低（低于 10 Gbps）。

协运站点数的选择有一个经验法则：取"可用站点数除以分存组大小"、"验货窗口总数"和"清单长度除以 2048"三者中的最小值。这保证每个站点至少处理 2048 个包裹（否则通信开销太大），不超过窗口总数（否则无法整除），且不超过可用站点数。

异步模式的选择建议：标准站点优先使用异步模式（搭配校准称重可最大化融合收益）；国产站点使用 RMS 称重时可用异步模式，使用标准称重时需要同步模式。

常见的故障排查：如果报"窗口数不能被站点数整除"的错误，换一个能整除的站点数；如果修正量不一致，检查修正量缩放的配置是否正确；如果爆仓，记住协运方案只减少中间件仓位，不减少工具仓位——需要同时开启拆箱共享制。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 经验法则 | Ulysses size 选择公式 |
| 分存组大小 | FSDP shard size |
| 中间件仓位 | Activation memory |
| 工具仓位 | Parameter memory |

**三条要点**：
- 协运站点数取"可用站点/分存组大小"、"窗口总数"、"清单长度/2048"三者最小值
- 异步模式在标准站点上几乎总是更优，国产站点取决于校准称重类型
- 协运只减少中间件仓位不减少工具仓位，大模型需同时开启拆箱共享制

### D.13 未来方向——协运网络的演进

**结论先行**：未来计划支持超长清单的环形传递、协运与分存的独立配置、动态调节协运站点数和多种分段方案的混合使用。

**物流解释**：

当前协运方案的干线互发要求每个站点持有完整清单，这对超长清单（百万包裹级别）仍有仓位压力。未来的上下文并行（Ring Attention）方案采用"环形传递"策略——站点们排成一个环，每个站点只向下一个站点传递自己的清单段，循环多轮后每个站点就与所有段做过验货了。这样无需一次性持有完整清单，适合更长的序列。

目前协运维度必须包含在拆箱共享制的管辖范围内（两者绑定），未来计划支持解耦——让协运组和分存组独立配置，更灵活地适配不同模型架构。

动态协运站点数是另一个方向：根据当前清单的实际长度自动调整参与协运的站点数，短清单用少量站点、长清单用更多站点，避免短清单场景下的通信浪费。

性能优化方面，未来可能在验货内部做更细粒度的通信-计算重叠（验货流水线），以及用半精度格式做干线互发以降低带宽需求。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 环形传递 | Ring Attention / Context Parallel |
| 协运与分存解耦 | Decoupled SP mode |
| 动态协运站点数 | Dynamic Ulysses Size |
| 验货流水线 | Intra-Attention pipelining |
| 半精度互发 | FP16/BF16 communication |

**三条要点**：
- 环形传递方案无需一次持有完整清单，可支持百万包裹级别的超长序列
- 协运与分存解耦将允许两种分工模式独立配置
- 动态站点数可以根据清单长度自动优化，避免短清单场景的通信浪费

## F. 常见误解纠正

**误解 1**："协运方案就是让每个站点各处理一段清单，互不干扰"
**纠正**：如果各段互不干扰，验货环节就无法工作——验货要求每个窗口看到完整清单。协运方案的核心正是通过干线互发让站点们在验货环节"看到完整清单的同时只负责部分窗口"，验完后再换回各自的段。"分段"和"互发"是不可分割的一对操作。
**为什么容易错**：只关注了"切段"忽略了"互发"

**误解 2**："同步模式和异步模式的最终结果不同"
**纠正**：两种模式的数值结果完全一致——测试中专门验证了这一点。区别仅在于调度策略：同步模式先发完再算，异步模式边发边算。就像快递是当天达还是次日达，包裹内容物完全一样。差异仅在效率上。
**为什么容易错**：异步往往暗示"不精确"或"近似"

**误解 3**："干线互发等同于全网对账（All-Reduce）"
**纠正**：干线互发（All-to-All）是"每个站点发不同的货给不同的站点"——站点 A 的一部分发给 B，另一部分发给 C。全网对账（All-Reduce）是"所有站点发相同类型的数据，求全局总和/平均"。干线互发后每个站点持有的数据不同（不同的验货窗口），全网对账后每个站点持有的数据相同（全局平均差异）。
**为什么容易错**：都是"多站通信"，容易混为一谈

**误解 4**："同步模式先 reshape 为 4D 再干线互发"
**纠正**：恰恰相反。同步模式在 3D 整体形态上直接做干线互发，互发完成后才拆分为 4D 窗口格式。异步模式才是先拆分为 4D 再互发。两种模式的维度转换顺序不同，这是实现层面的关键差异。
**为什么容易错**：直觉上觉得应该先拆好再发

**误解 5**："差异对账只需要把各站的差异值加起来求平均就行"
**纠正**：不能简单加起来求平均，因为每个站点的有效包裹数可能不同（由于填充料的存在）。必须用加权平均——先转成差异总和（差异值乘有效包裹数），全网汇总总和和总包裹数，再除以全局总包裹数。更关键的是，退货回传时的修正量需要额外乘以"协运站点数 * 本站包裹 / 全局包裹"来补偿拆箱共享制的除法效应。
**为什么容易错**：忽略了各段有效包裹数不同

**误解 6**："国产站点完全不支持异步模式"
**纠正**：国产站点支持使用 RMS 称重的异步模式（前向和反向都有国产实现）。只是标准称重（LayerNorm）仅有标准站点的实现。测试中跳过国产站点是因为测试恰好使用了标准称重。如果模型的校准称重使用 RMS 方式，国产站点可以正常运行异步模式。
**为什么容易错**：测试跳过 = 不支持的直觉判断

**误解 7**："协运方案能同时减少工具仓位和中间件仓位"
**纠正**：协运方案只减少中间件仓位（激活内存），不减少工具仓位（参数内存）——因为工具在协运组内是完全复制的。要减少工具仓位，需要同时开启拆箱共享制（FSDP）。两套方案各管各的：协运管中间件分段，分存管工具碎片。
**为什么容易错**："并行"往往暗示"什么都分了"

## G. 读者复述测试

**Q1 (Why)**：为什么同步模式在 3D 整体形态上做干线互发，而异步模式先拆分为 4D 窗口格式再做互发？这两种不同的顺序各有什么影响？

> **A**：同步模式在 3D 上互发是因为它一次性处理完所有维度转换，操作更简单直接。异步模式需要先拆分为窗口格式（4D），是因为它要把三联分拣和干线互发交织在一起——投影完一份立刻发出，需要按窗口维度拆好才能正确地散发给其他站点。这是通信-计算重叠的要求决定的。

**Q2 (What-if)**：如果某个站点在一个批次中所有包裹都是填充料（有效包裹数为零），差异对账会发生什么？系统如何避免崩溃？

> **A**：有效包裹数为零时，该站点的差异计算可能产生异常值（NaN）。底层对账模块（ReduceLoss）在发现有效包裹数为零时，会自动用异常值清除（nan_to_num）把 NaN 替换为零，然后正常参与全网汇总。该站点的差异贡献为零，不影响全局平均值的正确性。

**Q3 (How)**：在异步模式下，退货差异单回传（反向传播）是如何实现通信-计算重叠的？请描述前三步的具体交替过程。

> **A**：第一步，发出价值单（V）梯度的异步干线互发请求。第二步，在等待价值单回件的同时，计算校准称重（QK Norm）的反向修正——这利用了等待时间做有用工作。第三步，价值单回件到达后（如果有共用窗口则合并复制窗口的差异），立即发出索引单（K）梯度的异步互发，然后在等待期间计算价值投影的修正量。整个过程与前向传播镜像对称但顺序相反（V→K→Q）。

**Q4 (Why)**：为什么退货回传时的修正量需要乘以"协运站点数 * 本站包裹 / 全局包裹"？如果不做这个缩放会怎样？

> **A**：因为拆箱共享制（FSDP）默认会把修正量（梯度）除以它管辖的站点数（包含协运站点），但协运组内的站点共同处理同一份清单的不同段，它们的修正量应该累加而非平均。如果不做补偿缩放，修正量会被过度稀释——相当于每次调整工具时力度被缩小了 P 倍，导致训练收敛极慢甚至不收敛。

**Q5 (How)**：图文混装（VLM）货物的入库分拣为什么需要缩放倍数补齐？请用一个具体例子说明。

> **A**：假设协运站点数为 4，视觉处理会将每 4 个图像包裹合并为 1 个（缩放倍数 = 4），清单长度为 100。普通补齐只需凑到 4 的倍数（补到 100→100，恰好整除）。但合并后长度变成 25，不能被 4 整除。缩放倍数补齐要求凑到 4*4=16 的倍数（补到 100→112），合并后变成 28，能被 4 整除（每站 7 个）。如果不用缩放倍数，合并后的分段会不均匀，导致干线互发失败。
