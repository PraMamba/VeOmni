# 拆箱共享制（FSDP）与新一代拆箱共享制（FSDP2）：一个物流网络的故事

**本文是 [FSDP & FSDP2 Backend 深度分析](fsdp_fsdp2_backend_analysis.md) 的科普改写版。全文用物流隐喻替代代码和技术术语。零代码，全物流世界观。**

---

## A. TL;DR 故事

VeOmni 是一个大型物流网络的总调度系统。它要解决的核心问题是：当库存货物（模型参数）太多、一个仓库（GPU）放不下时，如何把货物拆分存放在多个站点（GPU），并在需要使用时快速组装还原。系统提供了两套拆箱共享方案——老式拆箱共享制（FSDP1）和新一代拆箱共享制（FSDP2），还能与分仓制（Expert Parallelism）配合，让专业仓库各自管理不同品类的货物。整套方案的核心权衡是：货物拆得越碎、每个仓库越轻松，但每次用货前"合并清单、取回全部货物"的通信成本就越高。

## C. 三层解释

### C.1 一句话版

一套物流系统把一个仓库装不下的工具拆分存放到多个站点，每次需要用时临时拼凑齐全，用完再拆开放回去，从而让每个站点都能处理超大批量的包裹。

### C.2 一段话版

想象你经营一个全国性的快递分拣网络，但每个分拣站的仓位容量有限，装不下全套分拣工具。拆箱共享制（FSDP）的做法是：把全套工具拆成若干份，每个站点只存一份，需要用时大家互相借调拼成完整工具，用完再拆回去。系统提供了两种拆箱方案——老式方案把所有工具打包成一个大箱子再切片，新方案则给每件工具贴上物流标签、保留原始形状。对于需要"专线分拣"的特殊件（专家模型），系统还叠加了分仓制——不同站点负责不同品类的包裹，各有各的专业工具。

### C.3 技术版（物流隐喻）

拆箱共享制（FSDP）是一种分布式仓储方案。假设一个站点（GPU）的仓位容量（显存）为 80GB，但全套工具（模型参数 7B 个、BF16 精度下 14GB）加上退货差异单（梯度 14GB）和优化器记账簿（56GB），总共需要约 94GB——超出了单站容量。

解决方案是将工具切成 N 份（N = 站点数），每个站点只存 1/N。发货出仓（前向传播）时，通过合并清单（All-Gather）通信原语从所有站点收集完整工具；回传回执（反向传播）后，通过对账后分摊（Reduce-Scatter）把退货差异单汇总并重新分配。这样每站只需存储约 20.5GB（参数 1.75GB + 梯度 1.75GB + 优化器 7GB + 中间产物约 10GB）。

老式拆箱制（FSDP1）采用合箱打包——把所有工具压平到一个大箱子里再切片，简单但丢失了原始结构。新一代拆箱制（FSDP2）则给每件工具贴上物流标签件（DTensor），保留原始形状，并支持更灵活的组合：可以按楼层（Transformer 层）逐层包装，专家模块和注意力模块使用不同的拆箱方案。

对于特殊件处理中心（MoE 层），系统在拆箱制之上叠加分仓制（EP）。128 个专业仓库（专家）先按仓号切分（沿维度 0 分片）分配到 8 组站点，每组只管 16 个仓库；然后在每组内再用拆箱制按货架层切分（沿维度 1 分片），进一步降低每站的存储压力。分仓版图（EP-FSDP DeviceMesh）独立于主版图，专门管理特殊件的分仓和拆箱。

## D. 逐章改写

### D.1 概述与设计目标

**结论先行**：VeOmni 提供了一套统一的物流网络调度系统，让调度员通过一个开关就能在三种配送模式之间切换。

**物流解释**：

VeOmni 的分布式训练系统就像一个全国性的物流调度中心。调度员面前有三个配送模式按钮：老式拆箱共享制（FSDP1）、新一代拆箱共享制（FSDP2）、和多站同款备货（DDP）。不同模式适用于不同场景——工具太多放不下就用拆箱制，工具不多但要提速就用同款备货。

系统的核心设计目标有四个：第一，统一调度接口，无论用哪种配送模式，调度员的操作流程相同；第二，分仓感知——当网络中有专线分拣的特殊件时，系统自动识别并启用分仓制；第三，支持轻量包装（混合精度），工具以较轻的包装运输、但重要环节用加厚包装确保精度；第四，统一的库存快照格式，无论哪种拆箱方案，快照格式都是统一的分布式快照（DCP）。

如果不提供这种统一接口会怎样？每种配送模式都需要独立的调度流程、不同的快照格式、不同的退货差异单处理方式——调度员的工作量会翻几倍，切换模式时容易出错。

代价是什么？统一接口意味着某些模式特有的高级功能需要特殊处理。比如老式拆箱制支持把工具暂存到办公桌（CPU Offload），但新一代拆箱制暂不支持。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 物流调度中心 | VeOmni 分布式训练系统 |
| 配送模式按钮 | `dp_mode` 参数 |
| 老式拆箱共享制 | FSDP1 |
| 新一代拆箱共享制 | FSDP2 |
| 多站同款备货 | DDP |
| 分布式快照 | DCP (Distributed Checkpoint) |

**三条要点**：
- 调度员通过一个配送模式开关即可在三种方案间切换，不需要改变整条运输线
- 系统自动感知分仓制的存在，为特殊件启用专用物流版图
- 统一快照格式保证了不管用哪种拆箱方案，库存快照都能互相读取

### D.2 核心架构与流程

**结论先行**：整套系统的运作分三个阶段——画版图、部署工具、日常运输循环，每个阶段都由调度员统一编排。

**物流解释**：

物流网络的运作从"画版图"开始。调度员根据站点数量、业务需求，绘制一张多维版图。版图的每个维度代表一种协作方式：有的维度管"谁和谁拆箱共享工具"，有的管"谁和谁分担不同品类的包裹"，还有的管"谁和谁协运同一份长清单"。

版图画好后进入"全网部署编排"。调度员先处理拆箱协作加工（TP）——如果一件工具太大，需要多个站点同时加工不同部分。然后处理数据并行的配送方案：选择老式拆箱制、新一代拆箱制、或多站同款备货。

日常运输循环是系统的核心。每个"车次"（训练步骤）包含以下环节：发货出仓时，合并清单通信取回完整工具；加工完成后回传回执，退货差异单通过对账后分摊汇总到各站；退货差异单封顶确保单次调整幅度不会过大；最后调整库存账（优化器更新）完成一个车次。

如果没有这种三阶段设计会怎样？版图、部署、运输三者耦合在一起，任何并行策略的变更都需要重写整条运输线——这在站点数达到数百个时是不可接受的。

代价是分层抽象引入了一定的调度开销——版图的初始化本身需要所有站点协调，这在启动阶段会消耗几秒到几十秒的时间。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 画版图 | `init_parallel_state()` |
| 全网部署编排 | `build_parallelize_model()` |
| 车次 | 训练步骤 (training step) |
| 发货出仓 | 前向传播 (forward pass) |
| 回传回执 | 反向传播 (backward pass) |
| 退货差异单封顶 | 梯度裁剪 (gradient clipping) |
| 调整库存账 | 优化器更新 (optimizer step) |

**三条要点**：
- 系统把"画版图"、"部署工具"、"日常运输"三个阶段解耦，各自独立变化
- 发货出仓和回传回执分别对应合并清单和对账后分摊两种通信模式
- 日常运输循环的每个环节都能感知分仓制的存在，对普通件和特殊件区别处理

### D.3 并行状态管理

**结论先行**：调度员为整个物流网络维护一份冻结的状态登记表，记录所有维度的编排信息，一旦确定就不再更改。

**物流解释**：

物流网络启动时，调度员会填写一份"并行状态登记表"。这份登记表记录了网络的所有编排维度：多少个站点参与多站同款备货？多少个站点共享同一套拆箱工具？有没有启用序列分段协运？有没有分仓制？用哪种拆箱方案？

登记表一旦填好就会被"冻结"——不可更改。这是一个关键的设计决策。为什么？因为在数百个站点同时运作的物流网络中，如果有人中途修改编排规则，可能导致某些站点用旧规则发货、另一些用新规则收货，整个网络就会陷入混乱。冻结确保了训练过程中的一致性。

登记表中最重要的属性之一是"拆箱通信组"——它返回的不是纯粹的分片组，而是包含了数据并行和序列并行所有站点的联合组。这意味着拆箱共享制的通信范围和损失对账的通信范围是一致的，保证了退货差异单封顶和损失缩放在同一个范围内计算。

另一个关键属性是"拆箱组规模"——计算方式是总站点数除以中转线数和拆箱协作组数。这个数字在损失缩放中用来补偿拆箱制默认的梯度除法。

登记表还记录了两张版图：主版图管理普通件的路由（包含复制区、分片区、协运区等维度），分仓版图管理特殊件的分仓和拆箱。两张版图相互独立但通过登记表关联。

如果没有冻结机制会怎样？中途修改维度会导致通信组不匹配——比如一个站点还在用旧的 8 站分片组发送数据，另一个站点已经切换到新的 16 站分片组接收，通信就会死锁。

代价是灵活性受限——训练过程中无法动态调整并行策略。如果需要调整，必须重启整个网络。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 并行状态登记表 | ParallelState 数据类 |
| 冻结 | `frozen=True` |
| 拆箱通信组 | `fsdp_group` (返回 `dp_sp` 组) |
| 拆箱组规模 | `fsdp_size` 属性 |
| 主版图 | 主 DeviceMesh |
| 分仓版图 | EP-FSDP DeviceMesh |
| 复合网格 | Flattened Mesh |

**三条要点**：
- 登记表冻结确保了数百个站点在整个训练过程中使用完全一致的编排规则
- 拆箱通信组包含了数据并行和序列并行的所有站点，保证梯度处理的一致性
- 两张版图——主版图管普通件，分仓版图管特殊件——相互独立但通过登记表关联

### D.4 老式拆箱共享制（FSDP1）

**结论先行**：老式拆箱制把所有工具合箱打包后切片分存，配合快照钩子自动处理分仓维度，适合稳定运行的生产环境。

**物流解释**：

老式拆箱制的工作流程分七步。

第一步，如果网络中有分仓制，先把特殊件的工具按分仓配送单进行分配——每个仓号对应的工具分到该仓号的站点。

第二步，制定包装策略。调度员根据版图形状决定用哪种拆箱方案。如果版图只有一维（所有站点在同一个分片组），就用"全拆"方案——工具、退货差异单、优化器记账簿全部切片。如果版图有两维（站内拆箱、站间复制），就用"混合拆箱"——站内全拆、站间复制。还有一种只拆退货差异单和记账簿、不拆工具本身的中间方案。这里有个扩展点：调度员可以接收外部传入的额外配置参数，覆盖默认的包装策略。

第三步，配置轻量包装。工具以轻量包装（BF16）存储和运输，但对账通信使用加厚包装（FP32）确保精度。缓冲区也用加厚包装。某些特殊模块（如分拣规则门控）需要高精度，可以通过模型自行声明来豁免轻量包装。

第四步，工具初始化。系统支持三种初始化模式：（A）每个站点各自准备一份工具，然后拆箱制自动分片；（B）0 号站点在办公桌上准备好全套工具，然后同步给所有站点；（C）先用"虚拟仓位"（Meta 设备）占位，不占实际空间，再从权重文件并行加载真实工具。第三种模式下，系统会转换权重文件的命名格式以确保与模型兼容。

第五步，应用拆箱包装。先把整个模型用拆箱制包装；如果有分仓制，再单独为每个专家模块包装——专家模块使用分仓拆箱版图中的拆箱子网格，并把退货差异单的除因子乘以分仓数，以补偿分仓带来的梯度分割。包装完成后，调用延迟初始化完成内部状态设置。

第六步，注册快照钩子。这些钩子在保存快照时自动为分仓参数添加分仓维度，加载时自动移除——调度员完全不需要手动处理。

第七步，如果启用了分仓制，把分仓感知的退货差异单封顶功能绑定到模型上。

如果不做第五步的延迟初始化会怎样？拆箱制的内部数据结构不会被正确设置，后续的合并清单和对账后分摊通信可能会出现不可预测的错误。

代价是什么？老式拆箱制的合箱打包会丢失工具的原始结构——调试时看到的是一个大箱子的切片，而不是单独的工具，这让问题定位变得困难。另外，快照钩子通过热插拔改装（Monkey Patch）修改了系统内部函数，升级系统版本可能导致兼容性问题。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 合箱打包 | FlatParameter |
| 全拆方案 | FULL_SHARD (ZeRO-3) |
| 混合拆箱 | HYBRID_SHARD (HSDP) |
| 只拆差异单和记账簿 | SHARD_GRAD_OP (ZeRO-2) |
| 虚拟仓位 | Meta 设备 |
| 快照钩子 | FSDPExtensions |
| 延迟初始化 | `_lazy_init` |
| 退货差异单除因子 | `gradient_postdivide_factor` |

**三条要点**：
- 老式拆箱制把工具合箱打包再切片，简单直接但丢失原始结构，调试困难
- 快照钩子通过热插拔改装自动处理分仓维度，调度员无感知，但升级系统有兼容风险
- 支持三种初始化模式——直接初始化、0 号站同步、虚拟占位后并行加载——适应不同场景

### D.5 新一代拆箱共享制（FSDP2）

**结论先行**：新一代拆箱制给每件工具贴上物流标签，保留原始形状，支持逐层精细控制，是新模型和复杂编排的首选方案。

**物流解释**：

新一代拆箱制的核心创新是物流标签件（DTensor）。与老式拆箱制的"合箱打包再切片"不同，新方案给每件工具单独贴上标签，记录这件工具存放在哪些站点、按什么维度切分。这保留了工具的原始形状，调度员随时可以看到"这是一把 4096x4096 的扳手，沿第二维切成 8 份"。

新一代拆箱制采用自底向上的部署策略。调度员先收集所有需要单独包装的楼层（Transformer 层），然后按"先里后外"的顺序包装：先包装专家模块（使用分仓拆箱版图），再包装高精度模块（不含轻量包装策略），最后包装整个楼层（使用主版图）。根模型最后包装。

配置参数中有一个重要的开关——前向后重新摆货。设为"是"（默认）时，发货出仓后立即把合并的完整工具拆回碎片，释放仓位；设为"否"时，保留完整工具在仓位中，回传回执时就不用再次合并清单，但占用更多仓位。还有一个"反向后重新摆货"开关，在攒单再对账（梯度累积）场景中尤为重要——中间微步可以不重新摆货，最后一步才释放，减少通信次数。

为什么专家工具沿货架层切分（维度 1）而不是沿仓号切分（维度 0）？因为维度 0 已经被分仓制使用了。假设原始有 128 个专业仓库的工具，分仓制沿维度 0 切成 8 份后每站只剩 16 个仓库的工具；再用拆箱制沿维度 1 切分，每站只需存储一小块。两种切分必须在不同维度上进行，否则会冲突。

当分仓制和新一代拆箱制同时使用时，自动预取不再可靠——系统不知道嵌套的分仓模块何时需要工具。因此必须手动配置预取：当前楼层计算时，提前为下一个楼层的模块取回工具。预取顺序是倒序的——后面先用的模块先预取。

新一代拆箱制要求所有模型必须使用"虚拟仓位"初始化——模型先在不占空间的虚拟设备上创建骨架，然后从权重文件加载到真实仓位。

如果不做手动预取会怎样？站点在需要工具时才发起合并清单请求，导致计算停滞等待通信完成——传送带会频繁空转，严重影响效率。

代价是什么？手动预取的配置增加了调度的复杂度。另外，新一代拆箱制暂不支持把工具暂存到办公桌（CPU Offload），对于超大模型是一个限制。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 物流标签件 | DTensor |
| 自底向上部署 | 手动 `fully_shard` 调用 |
| 前向后重新摆货 | `reshard_after_forward` |
| 反向后重新摆货 | `reshard_after_backward` |
| 沿货架层切分 | `Shard(1)` 分片 |
| 沿仓号切分 | `Shard(0)` 分片 |
| 手动预取 | `set_modules_to_forward_prefetch` |

**三条要点**：
- 物流标签件保留工具原始形状，调度员可以看到"这是什么工具、怎么切分的"
- 专家工具必须沿货架层（维度 1）切分，因为仓号维度（维度 0）已被分仓制占用
- 分仓制+新一代拆箱制必须手动配置预取，否则传送带会频繁空转

### D.6 分仓制（Expert Parallelism）集成

**结论先行**：分仓制让不同站点管理不同品类的专业仓库工具，通过分仓配送单声明式地定义哪些工具需要按仓号切分。

**物流解释**：

分仓制解决的是"专线分拣"的问题。在特殊件处理中心（MoE 层），128 个专业仓库各有各的工具——如果每个站点都存所有仓库的工具，浪费巨大。分仓制把这些工具按仓号分配：8 组站点各管 16 个仓库。

分仓配送单是一份声明式的配置文件，采用仓位地址通配符来匹配模型中的参数。例如，"所有楼层的专家进料工具、出料工具、门控工具，全部沿维度 0 分片"。配送单一旦生效，系统会：对每件匹配的工具创建全复制的物流标签件；然后重新分布为分片版本；提取本地分片替换原参数；并在参数上贴上分仓标签，记录它属于哪个分仓组、用什么放置策略。

分仓标签是一个元数据容器，记录三个关键信息：分仓拆箱版图（完整的分仓+拆箱二维版图）、放置策略（按仓号切分还是全复制）、以及参数的完全限定名称。这些信息在后续的退货差异单封顶和库存快照时都会用到。

配送单还提供了"获取免重复入库清单"的功能——告诉拆箱制"这些模块已经由分仓制管理了，不要再用你的规则去分片它们"。

如果没有分仓制会怎样？128 个专业仓库的工具全部复制到每个站点，光工具本身就可能占满仓位，根本没有空间放退货差异单和记账簿——网络根本启动不了。

代价是分仓制增加了通信复杂度——每次处理特殊件时，需要通过干线互发（All-to-All）把包裹发送到对应的专业仓库站点，加工完再发回来。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 分仓配送单 | ParallelPlan |
| 分仓标签 | SpecInfo |
| 仓位地址通配符 | FQN 模式匹配 |
| 免重复入库清单 | `get_fsdp_no_shard_info` |
| 干线互发 | All-to-All |
| 按仓号切分 | `Shard(0)` on expert dim |

**三条要点**：
- 分仓配送单用通配符声明式地定义哪些工具按仓号切分，调度员不需要逐个指定
- 分仓标签附加在每个参数上，让后续的封顶和快照都能感知分仓信息
- 分仓制和拆箱制通过"免重复入库清单"协作——各管各的模块，不互相干扰

### D.7 工具分片策略

**结论先行**：拆箱制提供了从"全拆"到"不拆"的多级拆箱方案，调度员根据仓位压力和通信带宽选择合适的级别。

**物流解释**：

拆箱方案的核心权衡是仓位占用与通信开销的平衡。

全拆方案（FULL_SHARD）把工具、退货差异单、记账簿全部切片。每个站点只存 1/N——仓位压力最小，但每次发货出仓和回传回执都需要合并清单和对账后分摊的通信——通信开销最大。适用于站内网络带宽充足的场景（如同一台服务器的多个站点之间有园区传送带连接）。

只拆差异单和记账簿（SHARD_GRAD_OP）保留完整工具在每个站点。好处是发货出仓时不需要合并清单——工具就在本地；坏处是每个站点需要额外存储完整工具——仓位压力增大。适用于模型较小但追求速度的场景。

混合拆箱（HSDP）是两级方案：站内全拆、站间复制。假设 4 台服务器各 8 个站点，站内 8 个站点全拆工具，4 台服务器之间则各自保留一份完整工具。这样合并清单只在站内高速通道上进行，站间只需要低频的同步。这是跨节点训练的常见选择。

对于新一代拆箱制，分片维度由一个函数决定。默认选择工具最大的那个维度来切分——这样切分后每块的形状更均匀。专家工具则强制沿维度 1 切分（原因见 D.5）。

如果选错拆箱方案会怎样？全拆方案在跨节点训练中可能因为节点间带宽不足而严重拖慢速度；不拆方案在大模型场景中可能直接爆仓。选择的关键依据是"仓位容量余量 vs 通信带宽"。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 全拆方案 | FULL_SHARD (ZeRO-3) |
| 只拆差异单和记账簿 | SHARD_GRAD_OP (ZeRO-2) |
| 混合拆箱 | HYBRID_SHARD (HSDP) |
| 不拆 | NO_SHARD (DDP mode) |
| 站内高速通道 | NVLink / 园区传送带 |
| 分片维度选择函数 | `shard_placement_fn` |

**三条要点**：
- 全拆方案仓位压力最小但通信最多，适用于带宽充足的站内场景
- 混合拆箱把全拆限制在站内、站间只做复制，是跨节点训练的务实选择
- 新一代拆箱制通过分片维度选择函数，让不同类型的工具选择最合适的切分维度

### D.8 退货差异单同步与封顶

**结论先行**：退货差异单封顶必须把分仓参数和普通参数分开处理，各自在不同的通信组上汇总，最后合并为一个统一的封顶系数。

**物流解释**：

退货差异单封顶的目的是防止"单次调整幅度过大"——如果差异单的总量超过阈值，就按比例缩小所有差异单。

在没有分仓制的普通场景下，封顶很简单：所有站点的差异单在拆箱通信组上做一次全网对账，算出全局总量，然后决定是否裁剪。

但分仓制的存在让事情复杂化了。分仓参数（专家工具）和普通参数存在于不同的通信组上——分仓参数只在分仓拆箱组和分仓组上有意义。因此，封顶必须分两路走：

普通参数路径：在拆箱通信组（整个数据并行+序列并行范围）上做一次全网对账，汇总全部普通参数的差异单总量。

分仓参数路径：先在分仓拆箱组（同一分仓内的拆箱站点）上对账——汇总同一批专家工具的差异单；再在分仓组（不同分仓的对应站点）上对账——汇总所有专家的差异单。两次对账缺一不可：第一次汇总"同一个专家在不同拆箱分片上的差异单"，第二次汇总"不同专家之间的差异单"。

两路汇总完成后，合并为一个总量，算出统一的封顶系数，然后应用到所有参数上。

老式拆箱制和新一代拆箱制在应用封顶系数时有一个细微差别：老式方案手动计算系数并逐个乘以差异单；新方案使用系统原生的封顶工具函数，代码更简洁且与生态更一致。

如果不分两路处理会怎样？分仓参数的差异单只在部分站点上有意义，如果混在一起全网对账，那些不持有对应分仓参数的站点会贡献 0 值，导致全局总量被低估，封顶阈值过于宽松——模型训练可能发散。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 退货差异单封顶 | `clip_grad_norm` |
| 拆箱通信组 | `fsdp_group` |
| 分仓拆箱组 | `ep_fsdp_group` |
| 分仓组 | `ep_group` |
| 全网对账 | All-Reduce |
| 封顶系数 | `clip_coef` |
| 原生封顶工具函数 | `clip_grads_with_norm_` |

**三条要点**：
- 分仓参数需要两次对账——先在分仓拆箱组内汇总同一专家的差异单，再在分仓组间汇总不同专家的差异单
- 两路汇总合并后，所有参数使用同一个封顶系数——保证全局一致性
- 新一代拆箱制使用系统原生的封顶函数，老式方案则手动计算——功能相同，实现风格不同

### D.9 轻量包装（混合精度训练）

**结论先行**：工具用轻量包装（BF16）运输和存储以节省仓位和加速，但对账通信必须用加厚包装（FP32）以保证精度。

**物流解释**：

轻量包装的核心思想是"运输时省空间，关键环节不马虎"。工具以 BF16 精度存储和运输——每件工具只占 2 字节而不是 4 字节，仓位压力减半。但对账通信时——汇总所有站点的退货差异单——必须转为 FP32 高精度包装。

为什么对账不能用轻量包装？假设 8 个站点各自有一份差异单，需要累加在一起。BF16 每次加法会引入约 0.1% 的误差，8 次累加后误差积累到约 0.8%。FP32 每次加法的误差只有 0.0001%，8 次累加后仅 0.0008%。对于需要训练数千步的物流网络来说，0.8% 的误差会随步数不断放大，最终导致调整方向偏离。

BF16 轻量包装相比 FP16 有一个关键优势：动态范围与 FP32 相同（8 位指数），不会出现"包裹太大装不下"（上溢）或"包裹太小看不见"（下溢）的问题，因此不需要额外的加厚泡沫（loss scaling）。

某些特殊模块——如分拣规则门控（MoE Router/Gate）——必须豁免轻量包装。因为分拣规则决定每个包裹的去向，微小的精度差异会导致包裹被发错目的地，影响整个分拣效率。这些模块可以通过模型自行声明来获得豁免。

在新一代拆箱制中，被豁免轻量包装的模块还会被设为"前向后不重新摆货"——因为它们需要高精度的完整工具常驻在仓位中。

多站同款备货（DDP）路径也支持轻量包装，但有一个细微差别：它的缓冲区用 BF16 而不是 FP32，与拆箱制的策略不同。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 轻量包装 | BF16 混合精度 |
| 加厚包装 | FP32 精度 |
| 加厚泡沫 | Loss Scaling |
| 分拣规则门控 | MoE Router/Gate |
| 豁免声明 | `get_ignore_modules_in_mixed_precision` |

**三条要点**：
- 轻量包装（BF16）让工具体积减半，但对账通信必须用加厚包装（FP32）避免误差累积
- BF16 的动态范围与 FP32 相同，不需要加厚泡沫，这是比 FP16 的关键优势
- 分拣规则门控等精度敏感模块必须豁免轻量包装，否则包裹会被发错目的地

### D.10 重新摆货控制

**结论先行**：调度员可以动态控制"什么时候把拼凑好的完整工具拆回碎片"，在攒单再对账场景中能大幅减少通信次数。

**物流解释**：

重新摆货是拆箱制的核心操作——合并清单取回完整工具后，用完要不要立即拆回碎片？这涉及两个时机：发货后（前向后）和回传后（反向后）。

前向后重新摆货：默认开启。发货出仓完成后，立即把完整工具拆回碎片放回各站——释放仓位。代价是回传回执时又需要重新合并清单取回完整工具。如果关闭，完整工具保留在仓位中，回传时不用再次通信，但占用更多仓位。

反向后重新摆货：在攒单再对账（梯度累积）场景中，训练脚本实现了一个巧妙的动态控制。假设要攒 4 批微单再统一对账：
- 第 1 到第 3 批微单：关闭反向后重新摆货。工具在反向传播后保持完整状态，下一批微单的前向可以直接使用，省去了合并清单通信。
- 第 4 批微单：开启反向后重新摆货。最后一批处理完成后，工具被拆回碎片，为调整库存账（优化器更新）腾出仓位。

这个优化减少了 3 次反向时的合并清单通信。代价是中间微步期间每个站点需要存放完整工具——仓位占用增大。适用于仓位充裕但通信是瓶颈的场景。

如果在所有微步都开启重新摆货会怎样？每次反向后都重新合并清单-分摊-合并清单，4 步累积变成 8 次通信而不是 5 次——对于带宽有限的跨节点训练，这 3 次额外通信可能占据总时间的 20%。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 前向后重新摆货 | `reshard_after_forward` |
| 反向后重新摆货 | `reshard_after_backward` |
| 攒单再对账 | 梯度累积 (gradient accumulation) |
| 微单 | 微批次 (micro-batch) |

**三条要点**：
- 前向后重新摆货默认开启，在仓位紧张时必须开启，否则完整工具会占满仓位
- 攒单再对账时，中间微步关闭反向后重新摆货，最后一步再开启——减少通信次数
- 这个动态控制是通信与仓位的经典权衡——通信是瓶颈时关闭，仓位是瓶颈时开启

### D.11 优化器集成

**结论先行**：分仓制+新一代拆箱制需要一个多优化器容器，因为分仓参数和普通参数在不同的拆箱维度上，无法共享同一个优化器。

**物流解释**：

优化器是"库存调整账本的管理员"——它根据退货差异单调整每件工具的库存。标准情况下，一个管理员就能管理所有工具。

但在分仓制+新一代拆箱制的场景下，事情变了。分仓参数（专家工具）沿维度 1 拆箱，普通参数沿维度 0 拆箱——它们的分片维度不同，物流标签件（DTensor）的元数据也不同。一个标准优化器无法同时理解两种分片格式。

解决方案是多优化器容器。它像一个总账本管理员，下辖两个子管理员：一个专管分仓参数，一个专管普通参数。对外呈现统一接口——调度员只需调用"调整库存"和"清空差异单"，容器会自动分发给两个子管理员。

保存快照时，容器把两个子管理员的状态字典合并为一份；加载时再拆分发回。合并时会检查键名冲突——确保不同子管理员管理的参数不重叠。

那为什么老式拆箱制+分仓不需要多优化器？因为老式拆箱制把所有参数都合箱打包为一个大箱子，然后统一沿维度 0 切片——不管是分仓参数还是普通参数，对优化器来说形状是一致的。

系统还提供了一种低精度优化器（AnyPrecisionAdamW），使用 BF16 存储动量和方差——相比标准 FP32 优化器节省 50% 的记账簿空间。它通过一种叫"精确累加补偿"的技术（Kahan 求和），把每次舍入产生的误差记录下来并在下一步补偿，避免 BF16 精度下的误差累积。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 多优化器容器 | MultiOptimizer |
| 总账本管理员 | MultiOptimizer 外壳 |
| 子管理员 | 子优化器 (EP/non-EP) |
| 精确累加补偿 | Kahan 求和 |
| 低精度优化器 | AnyPrecisionAdamW |
| 优化器记账簿 | 优化器状态 (exp_avg, exp_avg_sq) |

**三条要点**：
- 分仓参数和普通参数的分片维度不同，需要两个子优化器分别管理
- 多优化器容器对外统一接口，调度员不需要关心内部有几个子管理员
- 低精度优化器通过精确累加补偿技术，在 BF16 精度下也能保持准确的库存调整

### D.12 库存快照管理

**结论先行**：库存快照的核心挑战是分仓维度的处理——保存时要恢复分仓维度让快照格式完整，加载时要移除分仓维度让拆箱制正常工作。

**物流解释**：

分布式快照（DCP）格式的特点是"每个站点存自己的那份切片，元数据记录全局形状"。这样换站点数量时可以弹性恢复——新网络的站点可以从旧快照中提取需要的部分。

但分仓制让快照变复杂了。在日常运作中，分仓参数只有"拆箱"这一个维度——分仓维度已经在部署时就"消化"了，参数是本地的。但保存快照时，必须"恢复"分仓维度，让快照知道"这个参数不仅被拆箱切分了，还被分仓切分了"。

恢复分仓维度的做法：取出物流标签件的底层本地数据（不是调用"提取到本地"方法，因为那会丢失分片信息），然后在分仓拆箱二维版图上重建物流标签件，放置策略设为"维度 0 分仓、维度 1 拆箱"。

移除分仓维度的做法：加载的物流标签件有两个放置维度（分仓+拆箱）。系统取出底层本地数据，在拆箱子版图上重建只含拆箱维度的物流标签件——分仓维度就被"吸收"回本地了。

老式拆箱制通过快照钩子自动完成这些操作——保存时钩子自动添加分仓维度，加载时自动移除。新一代拆箱制则需要通过模型状态包装器手动处理。

优化器快照的处理逻辑类似——记账簿中每个条目的形状与参数形状一致，因此需要同样的分仓维度恢复/移除操作。唯一的区别是优化器状态字典的键名需要子串匹配来找到对应的分仓参数。

系统还支持异步快照保存——使用一条独立的通信线路（专用的 Gloo 进程组）来执行快照写入，不干扰训练通信。系统通过"未来承诺"跟踪异步保存进度，如果前一次保存未完成，会先等待完成再启动新的保存。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 分布式快照 | DCP (Distributed Checkpoint) |
| 恢复分仓维度 | `restore_ep_dim` |
| 移除分仓维度 | `drop_ep_dim` |
| 底层本地数据 | `_local_tensor` |
| 模型状态包装器 | `ModelState` |
| 优化器状态包装器 | `OptimizerState` |
| 独立通信线路 | 专用 Gloo 进程组 |
| 未来承诺 | `dcp_save_future` |

**三条要点**：
- 保存快照时恢复分仓维度，加载时移除——这对"维度进出"操作是分仓制与快照格式对接的核心
- 恢复维度时使用底层本地数据而不是"提取到本地"——保留拆箱分片信息不丢失
- 异步保存使用独立的通信线路，不干扰训练的主通信——但必须串行化，前一次未完成不能启动新的

### D.13 物流版图拓扑

**结论先行**：调度员通过构建矩阵变换来决定每个站点在分仓版图中的位置，就近分仓和跨区分仓各有适用场景。

**物流解释**：

物流版图是一张多维地图，描述"哪些站点在哪个维度上协作"。主版图记录普通件的路由——复制区、分片区、协运区的划分。分仓版图记录特殊件的分仓和拆箱关系。

分仓版图的构建涉及一个关键选择：就近分仓还是跨区分仓？

就近分仓（默认）：构建一个"拆箱数 × 分仓数"的矩阵，然后转置。结果是同一分仓的站点物理上相邻——比如站点 0、4、8、12、16、20、24、28 都属于分仓 0。这意味着分仓内的干线互发（All-to-All）通信会跨越节点，但拆箱组内的合并清单通信在同一列中——站点 0、1、2、3 是一个拆箱组，它们物理上在同一个节点内，通信快。

跨区分仓：直接按"分仓数 × 拆箱数"排列。同一分仓的站点物理上紧挨着——站点 0、1、2、3 是分仓 0。干线互发在节点内进行（快），但拆箱组的合并清单需要跨节点（慢）。

如何选择？如果分仓内的干线互发通信量大（专家数多、每次发大量包裹），选跨区分仓让它走节点内高速通道；如果拆箱组的合并清单通信量大（参数量大、频繁 all-gather），选就近分仓让它走节点内通道。

四种复合版图把基础维度组合起来：数据并行版图用于数据加载器的分布式采样；参数分片版图用于拆箱制的实际分片范围；损失对账版图用于损失值的全局对账；序列并行版图用于协运通信。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 就近分仓 | `ep_outside=False` (ep_inside) |
| 跨区分仓 | `ep_outside=True` |
| 矩阵变换 | `init_ep_mesh_matrix` |
| 复合版图 | Flattened Mesh |
| 节点内高速通道 | NVLink / 园区传送带 |

**三条要点**：
- 就近分仓让拆箱组通信走快速通道，跨区分仓让分仓内干线互发走快速通道
- 选择的依据是"哪种通信量更大"——通信量大的放在节点内
- 四种复合版图各有用途：数据采样、参数分片、损失对账、序列协运

### D.14 性能优化

**结论先行**：预取、攒单再对账、临时存单和损失缩放补偿是四大核心优化手段，各自解决通信延迟、通信次数、仓位压力和梯度精度问题。

**物流解释**：

**提前备货（预取）**：当前楼层还在加工时，提前为下一个楼层的模块取回工具。这样当前楼层完成时，下一楼层的工具已经到位，不需要等待。老式拆箱制有自动预取开关；新一代拆箱制在分仓场景下必须手动配置——系统按倒序设置预取顺序，后面先用的模块先取。

**攒单再对账（梯度累积）**：多个微单的差异单先累积，最后一次性对账。减少了优化器更新的频率。配合反向后重新摆货的动态控制，可以进一步减少通信次数。

**临时存单（激活检查点）**：发货出仓时不保存所有中间结果，只保存输入——回传回执时重新计算。这用计算时间换仓位空间。推荐使用非重入式检查点（PyTorch 2.0+），拆箱制会自动处理检查点与分片的交互。

**损失缩放补偿**：全局对账调度函数按每个站点的实际包裹数加权计算损失，而不是简单地除以站点数。关键公式是：每站损失乘以"本站包裹数/全局包裹数"，再乘以拆箱组规模。为什么要乘以拆箱组规模？因为拆箱制在对账后分摊时默认把退货差异单除以拆箱组规模——如果不预先补偿，最终的梯度会偏小。这个乘法精确地抵消了拆箱制的默认除法，让最终梯度反映真正的按包裹数加权。

**分组结构调试工具**：老式拆箱制包装完成后，系统会自动调用一个调试工具，以树形结构打印出每个拆箱组包含哪些模块、使用什么分片策略和轻量包装配置。设置日志级别为调试模式即可看到输出。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 提前备货 | Prefetch |
| 攒单再对账 | 梯度累积 |
| 临时存单 | 激活检查点 |
| 损失缩放补偿 | `mean_global_loss` 中的 `fsdp_size` 乘法 |
| 分组结构调试工具 | `verbose_fsdp_grouping` |

**三条要点**：
- 提前备货让通信和计算重叠，避免传送带空转——分仓场景下必须手动配置
- 损失缩放补偿乘以拆箱组规模，精确抵消拆箱制的默认梯度除法
- 临时存单用重新计算换取仓位空间——对于深层模型是训练大模型的必要手段

### D.15 限制与注意事项

**结论先行**：两种拆箱制各有限制，调度员需要根据系统版本、模型类型和硬件条件选择合适方案。

**物流解释**：

老式拆箱制的主要限制在于快照钩子的脆弱性。它通过热插拔改装修改了系统内部函数——这意味着每次系统版本升级都可能打破兼容性。另外，合箱打包丢失了工具的原始结构，调试时只能看到一堆编号而看不到"这是注意力权重还是前馈权重"。分仓制+老式拆箱制也无法使用手动预取，通信效率可能不如新方案。

新一代拆箱制的主要限制在于版本要求（系统 2.4 以上）和强制虚拟仓位初始化。不支持把工具暂存到办公桌（CPU Offload），对于超大模型是一个硬限制。分仓制+新一代拆箱制必须手动配置预取，增加了调度复杂度。

分仓制本身也有限制：仅适用于有专线分拣的特殊件处理中心（MoE 模型）；分仓参数必须沿维度 0 切分；暂不支持同时使用拆箱协作加工（TP）和分段中转线（PP）。

通用限制包括：序列并行必须包含在拆箱制中（无法解耦）；环形传递尚未实现（长清单分段处理受限）。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 热插拔改装的脆弱性 | Monkey Patch 兼容性问题 |
| 暂存到办公桌 | CPU Offload |
| 强制虚拟仓位 | `init_device="meta"` |
| 环形传递 | Ring Attention |

**三条要点**：
- 老式拆箱制稳定但脆弱——快照钩子依赖热插拔改装，升级系统可能打破兼容
- 新一代拆箱制灵活但严格——强制虚拟仓位初始化，不支持暂存到办公桌
- 分仓制暂不支持与拆箱协作加工和分段中转线同时使用——限制了多种模型并行的组合

## F. 常见误解纠正

**误解 1：** "拆箱共享制就是把模型复制到每个站点（多站同款备货）"
**纠正：** 恰恰相反。多站同款备货（DDP）是每站存一份完整工具，拆箱共享制是每站只存 1/N 份。拆箱制的核心是"拆"——把完整工具切碎分存，需要时再拼凑。正因为拆了，每站的仓位压力才能降低到可接受的水平。
**为什么容易错：** "共享"一词容易误导为"复制"

**误解 2：** "新一代拆箱制（FSDP2）是老式拆箱制（FSDP1）的简单升级，功能完全替代"
**纠正：** 两者有本质的架构差异。老式方案合箱打包后切片，新方案给每件工具贴标签保持原始形状。更重要的是，新方案不支持暂存到办公桌（CPU Offload），而老方案支持。它们是两种不同的设计理念，各有适用场景，不是简单的替代关系。
**为什么容易错：** 版本号暗示"后者优于前者"

**误解 3：** "分仓参数的退货差异单封顶只需要一次全网对账"
**纠正：** 分仓参数需要两次对账。第一次在分仓拆箱组内汇总"同一个专家在不同拆箱分片上的差异单"；第二次在分仓组间汇总"不同专家之间的差异单"。只做一次会导致全局总量被低估——因为不持有对应分仓参数的站点贡献 0 值。
**为什么容易错：** 普通参数确实只需一次对账

**误解 4：** "前向后重新摆货关闭就能一直省通信"
**纠正：** 关闭前向后重新摆货意味着完整工具常驻仓位——仓位占用翻倍。对于大模型来说，原本刚好放得下的仓位会直接爆仓。这个开关的合理使用是配合攒单再对账的动态控制——中间步骤不摆货、最后一步再摆货。
**为什么容易错：** "少通信=好"的直觉忽略了仓位限制

**误解 5：** "损失乘以拆箱组规模是为了放大损失"
**纠正：** 这个乘法是为了补偿拆箱制在对账后分摊时的默认除法。拆箱制会自动把退货差异单除以拆箱组规模，如果不预先乘上去，最终的梯度会偏小。乘法和除法精确抵消，让最终梯度反映的是按包裹数加权的正确比例，而不是简单的等分。
**为什么容易错：** 看到"乘以 N"直觉以为是放大

**误解 6：** "分仓版图和主版图用的是同一批站点，所以信息是重复的"
**纠正：** 虽然涉及相同的站点，但两张版图的维度划分完全不同。主版图按"复制区+分片区+协运区"划分，分仓版图按"分仓维度+分仓拆箱维度"划分。同一个站点在两张版图中的"邻居"可能完全不同——站点 0 在主版图中和站点 1 是同一个分片组，在分仓版图中和站点 4 才是同一个拆箱组。
**为什么容易错：** "同一批站点"暗示信息相同

**误解 7：** "恢复分仓维度时应该用'提取到本地'方法获取数据"
**纠正：** 必须使用"底层本地数据"（`_local_tensor`）而不是"提取到本地"（`to_local()`）。因为在新一代拆箱制下，参数已经是物流标签件——"提取到本地"会丢失拆箱分片信息。"底层本地数据"保留了分片状态，在此基础上重建包含分仓+拆箱两个维度的物流标签件才是正确的。
**为什么容易错：** 两个方法名字相似，功能却不同

## G. 读者复述测试

**Q1：** 为什么分仓参数（专家工具）在新一代拆箱制中必须沿维度 1（货架层）切分，而不能沿维度 0（仓号）切分？
> **A：** 因为维度 0 已经被分仓制（EP）使用了——128 个专业仓库先沿维度 0 切成 8 份，每站只剩 16 个仓库的工具。如果拆箱制也沿维度 0 切分，就会和分仓制冲突。因此拆箱制选择维度 1（隐藏维度/货架层）来切分，两者在不同维度上操作、互不干扰。

**Q2：** 如果在攒单再对账（梯度累积）场景中，所有微步都开启"反向后重新摆货"，会带来什么具体的性能损失？
> **A：** 每个微步的反向传播后都会把完整工具拆回碎片，而下一个微步的前向传播又需要重新合并清单取回完整工具。假设 4 步累积，这会多产生 3 次"合并清单"通信。动态控制的做法是中间 3 步保留完整工具，只在最后一步拆回——用更多仓位占用换取 3 次通信的节省。

**Q3：** 损失缩放补偿是如何保证按包裹数加权的梯度精度的？请描述拆箱制、损失公式和最终梯度之间的因果链。
> **A：** 因果链是：（1）VeOmni 的损失公式把每站损失乘以"本站包裹数/全局包裹数"再乘以拆箱组规模（`fsdp_size`）；（2）拆箱制在对账后分摊（reduce-scatter）时自动把退货差异单除以拆箱组规模；（3）乘法和除法精确抵消，最终梯度等于"损失 × 本站包裹占比"——实现了按包裹数加权。如果启用了序列并行，还会先在协运组内对账本站包裹数以获得正确的本地合计。

**Q4：** 在 32 个站点、4 路分仓的配置下，站点 0 在分仓版图（就近分仓）中的拆箱组成员是哪些站点？为什么？
> **A：** 站点 0 的拆箱组成员是 {0, 1, 2, 3}。就近分仓通过"拆箱数×分仓数"矩阵转置构建版图，结果是同一列的站点（纵向）属于同一拆箱组——站点 0、1、2、3 物理相邻在同一节点内，拆箱组的合并清单通信走节点内高速通道（NVLink/园区传送带），速度快。

**Q5：** 如果老式拆箱制的快照钩子在系统升级后失效，会导致什么问题？如何避免？
> **A：** 快照钩子通过热插拔改装（Monkey Patch）修改了系统内部的优化器状态字典函数。如果升级后这些内部函数的签名或行为改变，钩子会调用失败或产生错误的分仓维度处理——导致快照保存时分仓参数缺少分仓维度标记，或加载时维度不匹配直接报错。避免方法是使用新一代拆箱制（FSDP2），它通过模型状态包装器手动处理分仓维度，不依赖系统内部函数的热插拔改装。
